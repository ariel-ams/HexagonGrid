# Trustworthy UX Knowledge and Adoption Roadmap

## Purpose

This document strengthens the UX Oracle with sources that are authoritative, implementable, and maintained. It keeps durable usability guidance separate from fashion: agents should not introduce a pattern because it is popular, visually novel, or generated by a model.

## Evidence hierarchy

Use the highest applicable source. Record exceptions in the task or PR notes.

1. Legal, contractual, security, and accessibility requirements.
2. W3C standards and WAI implementation guidance.
3. The project's established design system and supported platform guidance.
4. Official design systems and service manuals from mature organizations.
5. Credible UX research and measured project evidence.
6. Trend reports, gallery sites, and inspiration. These can form a hypothesis only.

No lower-level source may override a higher-level source. Laws of UX are useful decision heuristics; they are not a substitute for research, accessibility testing, or product evidence.

## Knowledge added to the Oracle

### Accessible interaction is a release condition

- Target WCAG 2.2 AA unless the project specifies a stricter baseline.
- Prefer semantic HTML. Use ARIA only when native semantics cannot express the interaction.
- For a custom composite widget, follow the matching WAI-ARIA Authoring Practices pattern, including keyboard behavior and focus management.
- Verify automated findings plus keyboard-only use, visible focus, zoom/reflow, and a representative screen-reader flow. Automation is evidence, not proof.

### Research is continuous, not a final ceremony

- Express assumptions as questions about a user goal, context, or barrier.
- Validate the end-to-end task, not merely whether people prefer a screen.
- Include people with access needs when the task or product affects them.
- Feed findings into the backlog and make the next decision traceable to evidence.

### System consistency supports speed and trust

- Reuse the project's components, tokens, content patterns, and interaction conventions before creating a new primitive.
- Define responsive and state behavior together: loading, empty, error, success, disabled, permission-denied, and long-content cases as applicable.
- Design for the content and data that will exist, including localization, zoom, and narrow viewports.

### Current product implications

These are durable responses to current practice, not visual prescriptions.

- Adaptive interfaces: specify behavior at relevant viewport and container changes; do not rely on one desktop layout shrinking gracefully.
- AI-assisted features: state what the system is doing, show uncertainty or provenance when material, preserve user review and reversal, and avoid making consequential changes silently.
- Agent-compatible interfaces: semantic structure, labeled controls, predictable navigation, and keyboard operation improve both assistive-technology and automation reliability.
- Expressive visual trends: motion, glass, large type, gradients, and novel controls need a job to do. Respect reduced-motion preferences and preserve contrast, readability, and task completion.

## Agent decision rule

For each UI change, classify every proposed choice as one of the following before implementation:

| Class | Agent action |
| --- | --- |
| Requirement | Implement and verify; an exception needs an explicit owner and rationale. |
| Established project pattern | Reuse it; document any intentional deviation. |
| Hypothesis | Define the expected user outcome and a validation method. |
| Decoration | Remove it unless it improves comprehension, hierarchy, feedback, or brand expression without harming access. |

## Roadmap

### Phase 0: establish the baseline

Owner: product and engineering leads.

- Confirm the supported platforms, browser/device range, design-system source, accessibility baseline, and existing test commands.
- Add the Oracle files and root `AGENTS.md` routing.
- Create a `ui-development/project-profile.md` using the template in the project usage guide.
- Select one representative journey and record its known defects, task-success signal, and baseline accessibility results.

### Phase 1: pilot on small UI changes

Owner: the delivery team.

- Apply the Oracle to two or three low-risk changes.
- For each change, write a compact UX intent, state matrix, and proportionate test plan before coding.
- Run the mandatory checks from the agent process and capture the result in the PR template when a PR exists.
- Review false positives, missing checks, and unnecessary ceremony.

Exit condition: checks catch at least one meaningful issue or the team can justify that the pilot surface was already compliant.

### Phase 2: standardize the feedback loop

Owner: engineering lead and design-system owner.

- Convert repeatable assertions into component, interaction, and accessibility tests.
- Add automated checks to CI where the project supports them; keep keyboard, screen reader, and visual review explicitly human-verified.
- Add or repair components/tokens for repeated exceptions rather than encoding one-off fixes.
- Track validation gaps as backlog work, not as undocumented debt.

Exit condition: a typical UI task can follow the routing map, use known patterns, and report verification without rediscovering the process.

### Phase 3: measure and improve

Owner: product, research, design, and engineering together.

- Review task success, abandonment, support contacts, accessibility defects, and usability findings at a regular product cadence.
- Turn evidence into prioritized changes; retire trends that did not produce the intended outcome.
- Refresh sources and the project profile every six months or after a platform/design-system change.

Exit condition: UI decisions are traceable to user outcomes, requirements, or validated project conventions.

## Proportionate verification

| Change type | Minimum validation |
| --- | --- |
| Copy, spacing, color, or static visual adjustment | Existing-token/pattern check, contrast where applicable, responsive visual review. |
| Interactive control or form change | Above, plus focused keyboard/focus/error-state coverage and behavior test when a test framework exists. |
| Custom widget, navigation, modal, or multi-step journey | Above, plus applicable APG pattern, interaction tests, screen-reader check, and end-to-end task check. |
| AI-assisted or consequential action | Above, plus confirmation/reversal, failure/uncertainty states, and human review of the user-control model. |

## Source register

- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/): normative accessibility success criteria.
- [WAI-ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/): accessible interaction patterns and keyboard behavior.
- [W3C accessibility evaluation guidance](https://www.w3.org/WAI/test-evaluate/): combines automated and manual evaluation.
- [U.S. Web Design System accessibility guidance](https://designsystem.digital.gov/documentation/accessibility/): component and multi-mode testing practices.
- [GOV.UK guidance on continuous user research](https://www.gov.uk/service-manual/user-research/how-user-research-improves-service-design): research through delivery, focused on user outcomes.
- [GOV.UK accessibility guidance](https://www.gov.uk/service-manual/helping-people-to-use-your-service/making-your-service-accessible-an-introduction): accessibility from discovery through live service.
- [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/): platform hierarchy, consistency, adaptation, and accessibility guidance.
- [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework): trustworthy, human-centered risk management for AI-enabled experiences.
- [Laws of UX](https://lawsofux.com/): concise behavioral heuristics used by the core Oracle.

Review this register every six months. Add a source only when it is authoritative for its scope, current enough for the project, and can change an agent decision or verification step.
